Core concepts

Five ideas explain the whole runtime: capabilities, specs, synthesis, executors, and contracts.

The pipeline

request → resolve capabilities → match agents → synthesize the gaps → build graph → execute → structured output

Everything runs through one function, agentmesh.core.runtime.run_project(). The CLI and the FastAPI app are both thin wrappers over it, so the two entry points cannot drift apart.

Capabilities

A request is reduced to a list of capabilities — sql_analysis, pii_detection, report_generation. Agents advertise the capabilities they cover, and the matcher connects the two. Nothing in the runtime hardcodes an agent name.

Known limitation. Capability resolution is keyword matching over the request text today. It is deliberately simple and it is the next thing to replace — see the roadmap.

Agents are YAML

Most agents need no Python at all. A spec with an output contract runs on the generic model-backed executor, where the spec is the prompt: the description sets the role, the capabilities scope the work, and the contract defines the JSON that must come back.

id: sql_analyzer_agent
name: SQL Analyzer Agent
category: data_ops
description: Reviews SQL for correctness, safety and performance risks.
capabilities:
  - sql_analysis
  - query_review
depends_on: []
output_contract:
  format: json
  required_fields: [findings, risk_level, suggested_changes, confidence]
models:
  default: anthropic/claude-opus-5
  fallback: [openai/gpt-4.1-mini]
validation:
  strict_json: true
  confidence_threshold: 0.75

Specs are validated with extra="forbid", so a typo'd key fails loudly at load time instead of being silently ignored.

Synthesis: agents that don't exist yet

When a required capability has no matching agent, AgentMesh builds one for it and runs it. The run reports the gap in missing_capabilities either way, so nothing is hidden — but the work still gets done.

$ agentmesh run -p data_ops "Research the options and summarize them."

┃ ID                       ┃ Origin      ┃ Level ┃
│ domain_research_agent    │ synthesized │   0   │
│ option_generation_agent  │ synthesized │   0   │
│ report_agent             │ spec        │   1   │

Synthesized agents are ephemeral. Re-run with --save-agents to keep them.

Ephemeral by default

Synthesized agents vanish when the run ends. Nothing is written to disk unless you ask:

agentmesh run -p data_ops "..." --save-agents

Saved agents land in the project's agents/ directory as ordinary specs, so the next run loads them from disk and synthesizes nothing. An agent you keep is indistinguishable from one you wrote by hand. Use --no-synthesize to turn the behaviour off entirely.

Executors

Every spec names an executor; the default is generic, the model-backed one. Register your own when an agent needs real code:

from agentmesh.agents.base_agent import BaseAgent
from agentmesh.agents.registry import register_executor

@register_executor("sql_analyzer")
class SqlAnalyzerAgent(BaseAgent):
    def run(self, message, context):
        # self.broker.resolve(self.spec) gives you a metered, retrying model call
        ...
executor: sql_analyzer

Retries, timing, token accounting and cost tracking live in the object the broker hands you, so any executor anyone writes gets all of it for free.

Output contracts

output_contract.required_fields is enforced. If the model returns JSON missing a required field, the field list is attached to the output as contract_violations rather than being quietly accepted. Unparsable responses are flagged the same way, with the raw text preserved.

{
  "agent_id": "sql_analyzer_agent",
  "summary": "...",
  "contract_violations": ["risk_level", "confidence"]
}
