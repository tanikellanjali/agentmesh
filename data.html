Data & connectors

An agent declares what data it needs. You bind that to your own source. The spec is portable; the data never moves.

Three layers

Putting connection details in an agent would make it unshareable. Splitting them is what lets one published agent run against many tenants' data.

# 1. REQUIREMENT - part of the agent spec. Public. Portable.
data_requirements:
  - name: transactions
    kind: table
    required_columns: [date, amount, supplier_id]
    description: Historical purchase transactions
# 2. BINDING - tenant-owned. Never travels with the agent.
registry.bind("transactions", source="warehouse", ref="analytics.purchases")
# 3. SOURCE - tenant-owned, credentialed.
registry.add_source(SqlAlchemySource("warehouse", url=os.environ["WAREHOUSE_URL"]))

Publishing an agent ships layer 1 only. Someone installs it, is told "this needs a transactions table with these columns", and points it at their own. It also makes agents testable — bind the requirement to a CSV fixture.

Handles, not payloads

Tools receive something they can query, never a pile of rows.

def supplier_spend(ctx, since: str):
    rows = ctx.table("transactions").query(
        "SELECT supplier_id, SUM(amount) FROM {table} WHERE date >= :since GROUP BY 1",
        since=since,
    )
    return summarize(rows)   # only this reaches the model

Cost

A margin calculation over 400k rows costs zero tokens. It queries, computes, returns a number.

Security

The model provider never sees raw customer data. Data minimisation is most of a security review.

Correctness

The database does the arithmetic, not a language model.

Sources

SourceCoversExtra
DuckDbSourceCSV, Parquet, JSON, globs — correct type inference, pushdown[duckdb]
SqlAlchemySourcePostgres, MySQL, Oracle, SQL Server, Snowflake, SQLite[sql]
SqliteSourceIn-memory tables, zero dependencies—
CsvSourceDeprecated. Reads every column as TEXT—
Why CsvSource is deprecated. It typed every column as TEXT, which makes units > 100 a string comparison — returning every row instead of the right one. DuckDbSource infers BIGINT, DOUBLE and DATE correctly. It is kept only so a bare install has a file source.

Every query is gated

authorize → estimate cost → check budget → execute → record

Writes are refused before they reach the database, identifiers are validated, results are capped and flagged when truncated, and every query lands in telemetry with rows, bytes, cost and duration.

>>> source.query("sales", "DELETE FROM {table}")
DataError: source 'warehouse' is read-only; refusing a mutating statement

Cost before you spend it

Queries can be priced before execution, so an agent can refuse an expensive one rather than discovering the bill afterwards.

estimate = ctx.table("transactions").estimate("SELECT * FROM {table}")
# bytes_scanned, cost_usd, exact

Set a ceiling and a query that would cross it never runs:

DataBudgetExceeded: query would scan 4,203,551,608 bytes (~\$21.0178);
that exceeds the \$5.0000 data ceiling (spent \$0.0000).
