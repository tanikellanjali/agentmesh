Governance & access

The problem this exists for: teams grow duplicate agents nobody can see, govern or reuse. Identity and policy are carried from the first call, not bolted on later.

Two dimensions, not one

"Granular" means actions and capacity are separate. Conflating them is why most permission models end up as a single useless boolean.

viewuseforkversioneditpublish
Agentread its specrun itcopy itmake v2change v1change visibility
Toolsee itcall it————
Data sourcesee schemaquery it————
Modelsee itspend on it————

Capacity is the other axis: max spend, which models, how many runs, which data scopes. "May use financial_agent, on Haiku only, capped at \$5/day" is a normal ask and is not expressible as a boolean.

Invisible vs blocked — the distinction that matters

If denied agents were simply filtered out, the resolver could not tell "nothing exists" from "you are not allowed", and would synthesize a replacement. Every denial would become a bypass.

Principal canResultWhy
not viewInvisible — synthesis proceeds freelyNo metadata leak: they are never told it exists
view but not useBlocked, explained, offer to create their ownEnforcement holds; the user understands why
view and useReused as-isThe point of a registry
result = catalog.search(principal, capabilities=["financial_analysis"])
result.usable    # agents they may run
result.blocked   # exist, visible, denied -> do NOT synthesize around these

Agents carry identity

id: sql_analyzer_agent
version: 2
owner: data-platform
visibility: org          # private | team | org | public
derived_from: sql_analyzer_agent@1

Adapting an agent creates a new version of the same agent, not a new agent. One identity, one history, and every run records which version executed.

Tools are the real boundary

An agent is a prompt and a contract. A tool is what touches the database, the filesystem, the payment API. If someone can fork an agent and point it at tools they already have, agent-level permission bought nothing. Agent permissions are governance; tool and data permissions are security. Enforcement belongs at tool invocation — one chokepoint.

A library cannot enforce this

AgentMesh reads YAML from disk and uses your own key. If policy lives in that YAML, you edit the YAML. Every check is advisory. The default authorizer says so plainly:

Decision(allowed=True, reason="no policy configured (AllowAll)")

Real enforcement needs a host that owns the catalog and runs the mesh server-side. The library defines three interfaces so that host is buildable without re-architecting anything:

InterfaceLibrary defaultHost application
CatalogYAML on diskDatabase with versions and ownership
AuthorizerAllowAllPolicy engine, identity, SSO
TelemetrySinkLoggerRows in a table, dashboards
run_project(
    "data_ops", message,
    principal=Principal(id="anjali", org="acme", teams=("data",)),
    authorizer=my_policy_engine,
)

Every model call, tool run and query is attributed to that principal — which turns the telemetry into an audit trail rather than debug logs.
