Resolution

How a request becomes a mesh: which agents to reuse, which to adapt, and what to create. This is the part that exists to stop teams growing duplicate agents.

Three decisions

A resolver is shown the request, the agents the caller may see, and every tool available. It prefers reuse over adaptation, and adaptation over creation — duplicated agents are the problem the system exists to prevent.

DecisionWhenResult
ReuseAn existing agent already covers itRuns as-is
AdaptAn agent is close but needs a capability or toolA new version of that same agent
CreateNothing in the catalog covers itA new agent, deterministic where possible

No fixed vocabulary

Capabilities are named from the request. Ask about translation and legal risk, and that is what comes back:

{
  "capabilities": ["sql_analysis", "translation", "legal_risk_review"],
  "reuse": ["sql_analyzer_agent"],
  "adapt": [{"id": "report_agent", "version": 3,
              "reason": "needs to summarise legal risk too"}],
  "create": ["translation_agent", "legal_risk_agent"],
  "blocked": ["finance_agent"],
  "source": "model"
}

Adaptation versions, it does not fork

adapted: report_agent v3   derived_from=report_agent@2
         capabilities: ['report_generation', 'legal_summary']

One identity, one history. Every run records which version executed.

Denial blocks — it is never routed around

An agent the caller can see but may not use is reported as blocked. The resolver does not invent a replacement, because that would turn every denial into a bypass. An agent they cannot even see is absent from the catalog entirely, so creating an equivalent is legitimate rather than an escape hatch. See Governance.

A denied agent is also never shown to the planner, so nothing leaks about its existence.

The plan is validated, not trusted

  • Agent ids that are not in the catalog are dropped, and the reason is recorded
  • Tool names that do not exist are stripped from created agents
  • An agent named twice is only created once
  • deterministic is ignored unless the agent actually has tools

Resolvers

ResolverUsesWhen
modelA model plans the meshDefault when a real provider is configured
catalogTerm overlap against the catalogFallback; no model is called
keywordThe original capability matcherLegacy, still available
run_project("data_ops", message, resolver="model")

With no resolver named, AgentMesh auto-selects: a model plans when one is reachable, and the deterministic matcher runs when it is not. A mock provider cannot plan a mesh, so it is not asked to — and the plan's source field always says which path ran.
