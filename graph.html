The agent graph

Agents run in dependency levels, not a fixed order. Independent agents run concurrently, and the final answer comes from a designated composer rather than whichever agent finished last.

Levels are derived by topological sort. Within a level, order is by id so runs are reproducible.

Declaring dependencies

id: data_quality_agent
depends_on:
  - ingestion_agent

An agent with no depends_on lands in level 0 and runs immediately. An agent that declares dependencies waits for all of them.

The composer rule

An agent whose capabilities include response_composition is the composer. It implicitly waits for every other agent and owns the run's final response.

This replaces a hardcoded ordering table and fixes a real bug: previously final_response was simply the last execution, so a late-running agent could silently overwrite the report with its own output.

Explicit depends_on always wins over the implicit rule. An agent that deliberately runs after the composer is supported — the composer's implicit dependencies exclude anything placed downstream of it, so declaring "run after the report" cannot create a cycle.

Concurrency

Agents in the same level have no dependency on each other, so they execute in a thread pool. Model calls are IO-bound, which is exactly the case threads handle well.

agentmesh run -p data_ops "..." --max-workers 8   # default 4
agentmesh run -p data_ops "..." --max-workers 1   # fully serial

Each agent in a level reads a snapshot of what earlier levels produced; their outputs merge once the level completes. That keeps parallel execution deterministic in its inputs.

Context flows downstream

Downstream agents receive upstream output in their prompt. You can see it in the token counts — the composer reads far more input than the level-0 agents because it is actually being given their work:

┃ Agent              ┃ Calls ┃  In ┃ Out ┃
│ data_quality_agent │     1 │  23 │  30 │
│ sql_analyzer_agent │     1 │  23 │  30 │
│ report_agent       │     1 │ 208 │  30 │   ← reads both

Invalid graphs fail early

The graph is built before any model is called, so a bad topology costs nothing:

ProblemResult
Dependency on an agent that isn't in the runGraphError: Agent 'x' depends on unknown agent(s): y
Agent depends on itselfGraphError: Agent 'x' depends on itself
Cycle between agentsGraphError: Circular dependency between agents: a, b

Inspecting the graph

Every run reports its levels. Over the API they come back under graph:

{
  "graph": {
    "levels": [["data_quality_agent", "sql_analyzer_agent"], ["report_agent"]],
    "final_agent": "report_agent"
  }
}
