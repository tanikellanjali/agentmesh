Execution & the graph

AgentMesh decides which agents run and why. How they run is a swappable engine.

Dependencies

id: data_quality_agent
depends_on:
  - ingestion_agent

An agent with no depends_on runs immediately. An agent with response_composition is the composer: it implicitly waits for everyone else and owns the final response.

This replaced a hardcoded ordering table and fixed a real bug — final_response used to be whichever agent ran last, so a late agent could silently overwrite the report with its own output.

Explicit depends_on always wins. An agent that deliberately runs after the composer works: the composer's implicit dependencies exclude anything downstream of it, so "run after the report" cannot create a cycle.

Two engines

NativeEngineLangGraphEngine
DependenciesNone[langgraph]
ParallelismLevel-synchronousPer-edge — a node starts when its deps finish
Checkpoint & resumeNoYes
Human-in-the-loopNoYes
StreamingNoYes

Both produce identical results — same agents, same levels, same final response, same call count. Swapping is configuration, not a rewrite.

Supervision, which is the point

Pause the mesh before a sensitive step, let a person look, then resume from the checkpoint.

from langgraph.checkpoint.memory import MemorySaver

engine = LangGraphEngine(
    checkpointer=MemorySaver(),
    interrupt_before=["response_composition_agent"],
)
paused after : ['spend_analysis_agent']
next node    : ('response_composition_agent',)
-- a human reviews, then approves --
after resume : ['response_composition_agent', 'spend_analysis_agent']

Context flows downstream

Downstream agents receive upstream output. You can see it in the token counts — the composer reads far more input because it is actually being given their work:

┃ Agent              ┃ Calls ┃  In ┃ Out ┃
│ data_quality_agent │     1 │  23 │  30 │
│ sql_analyzer_agent │     1 │  23 │  30 │
│ report_agent       │     1 │ 208 │  30 │   ← reads both
